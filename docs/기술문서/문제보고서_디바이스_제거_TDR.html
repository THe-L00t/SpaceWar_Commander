01한 장 요약

교수님 PC(RTX 5080)에서 클라이언트를 실행하면 20~30초 뒤 게임이 멈추고, D3D12 가 DXGI_ERROR_DEVICE_HUNG 사유로 디바이스를 제거한다. 그 뒤에 프로세스의 커밋 메모리가 선형으로 늘어 수 분 안에 64GB 에 이르고 화면이 검게 된다. 관찰 2026-09-08

즉 순서는 GPU 멈춤 → TDR → 디바이스 제거 → 메모리 폭주 다. 8월 26일 덤프에서 확인한 «드라이버가 32MB 푸시버퍼를 회수하지 못하고 1,985회 새로 잡았다» 는 사실 실측 은 그대로 유효하지만, 그것은 죽은 디바이스에 우리 렌더 루프가 계속 커맨드를 제출한 결과 다. 원인이 아니다.

드라이버를 616.64 로 올린 뒤에도 같은 증상이 났으므로, 이전 보고서의 1순위(610.62 결함)는 기각한다. 관찰

남은 미지는 하나

왜 실행 20~30초(8월에는 1~2분) 뒤에 GPU 가 커맨드 하나를 2초 넘게 끌게 되는가. 현재 판단은 RT 경로(인라인 RayQuery + 매 프레임 TLAS 재빌드 + UPLOAD 힙의 BLAS 입력)가 Blackwell 에서 병리적 입력을 만난다 이다. 판단 · 확신도 중 근거와 반증 조건은 05절.

4.2 · 왜 «선형» 으로, 왜 100ms 로 기어가는가 판단 · 덤프와 정합

교수님 PC 의 드라이버는 죽은 디바이스에 대한 제출을 즉시 거부하지 않고 약 100ms 안팎 대기한 뒤 새 푸시버퍼로 처리 하는 것으로 보인다. 덤프의 «메인 스레드가 nvwgf2umx 안에서 대기», «dt 가 100ms 천장에 붙음», «드라이버 워커 7개가 7분 내내 0.02초(회수 작업 없음)» 가 전부 이 설명과 맞는다. 초당 약 10회 제출 × 32MB ≈ 320MB/s 이므로 63GB 까지 3~4분이다. 덤프 시점 수명 7분에서 8월의 onset(1~2분)을 빼면 남는 시간과 부합한다.

개발 PC 실험(2.3)에서 메모리가 늘지 않은 이유는 드라이버와 GPU 가 달라 죽은 디바이스에 대한 제출을 다른 경로(즉시 실패, 할당 없음)로 처리 했기 때문이다. 그래서 그 실험은 «폭주» 였고 교수님 PC 는 «기어감» 이었다. 두 관찰은 모순이 아니라 단계 C 의 드라이버별 차이 다.

결론

메모리 폭주의 주체는 드라이버가 맞지만, 방아쇠는 «디바이스 제거 뒤에도 제출을 멈추지 않은 우리 루프» 다. 이 단계는 우리 코드로 끊을 수 있다(07절 ①).

05디바이스 제거(단계 B)의 원인 — 현재 판단

5.1 · 후보를 거르는 두 관문

  1. onset — 실행 후 20~30초(9월) 또는 1~2분(8월)에 처음 발생한다. 시작 직후가 아니다.
  2. PC 특이성 — RTX 5080(Blackwell)에서 재현, RTX 4070 Laptop(Ada)에서 미재현. 드라이버 610.62·616.64 모두 재현.

여기에 이번 관찰이 더한 조건: PROCESS_AT_FAULT(우리 커맨드가 실행 중), RT ON, 단일 클라.

5.2 · 후보 순위

1순위RT 경로 — 인라인 RayQuery 트래버설 또는 매 프레임 TLAS 빌드가 Blackwell 에서 2초 넘게 걸림

근거. RT ON 상태에서만 관측됨. Ada 에서 미재현. 8월의 «TLAS 재빌드 무해» 실험은 Ada + 610.88 조건이라 Blackwell 을 대변하지 못함. PROCESS_AT_FAULT.

약점. RT OFF 관측이 없다(반증 데이터 부재). 왜 20~30초 뒤인지 설명 못 함.

다음 발생 때 로그로 갈리는가. 예. DRED 자취의 마지막 커맨드가 BuildRaytracingAccelerationStructure 또는 RayQuery 를 쓰는 드로우인지로.

1-aBLAS 입력이 UPLOAD 힙 (main 구성, GRenderer.cpp 456~497)

비표준 사용. 빌드는 시스템 메모리에서 정점을 읽는다. 세대마다 처리가 갈릴 수 있음. 정석화 수정(0548b5d)이 있었으나 main 에 없음. 약점: BLAS 빌드는 메시 생성 시 1회라 onset 을 설명 못 함. 트래버설은 BLAS 결과(DEFAULT)만 읽음.

1-b비유한·극단 인스턴스 변환이 TLAS 에 들어감

main 의 원격 플레이어 노드는 퇴장 시 y = −1.0e7 로 주차(main.cpp 198, 321) → TLAS AABB 가 1만 km. 네트워크 좌표가 NaN/inf 면 BVH 가 손상돼 트래버설이 폭주할 수 있음. 약점: 이번 관찰은 단일 클라라 원격 노드가 없었을 가능성이 큼(서버가 유령 항목을 보내지 않는 한). 8월 세션(3클라)에는 해당. 갈림: 인스턴스 변환 로그로.

1-c광선 입력의 NaN/inf — 퇴화 삼각형의 노멀, 카메라가 표면 안쪽

Forward.hlsl 은 normalize(i.nrm)·reflect(-V, N) 을 검사 없이 광선으로 쓴다. NaN 방향 광선은 DXR 규격상 미정의 동작. 약점: 왜 Ada 에서는 무해한지 설명 필요(하드웨어별 미정의 동작이라 가능은 함). 갈림: 셰이더 가드 추가 뒤 사라지면.

1-dBlackwell 드라이버의 DXR 1.1 인라인 RT + PREFER_FAST_TRACE 매 프레임 재빌드 조합 결함

610.62·616.64 모두 재현 → 특정 빌드 결함이 아니라 브랜치·세대 결함일 수 있음. 약점: 우리 쪽 정화·리핏·DEFAULT 힙을 다 하고도 남아야 확정. 갈림: 소거법으로만.

2순위디버그 계층

근거. 8월·9월 모두 Debug 였다(분리된 적 없음). 덤프 스택의 최다 모듈.

약점. 디버그 계층은 CPU 쪽 검증이라 GPU 커맨드 실행 시간을 2초로 늘릴 기전이 없다. 단계 C 의 대기 스택에 보이는 것은 경로일 뿐. 갈림: Release 실행 기록이 생기면.

3순위래스터 측 (2400m 패치 대형 드로우, 드로우당 32비트 루트 상수)

근거. 없음. 약점. 20~30초 안에 변하는 요인이 없고 Ada 에서 멀쩡. 낮음.

5.4 · 현재 판단 한 문장 판단 · 확신도 중

main 구성에서 RT 를 켠 채 서버에 연결해 플레이하면, 실행 20초~2분 사이의 어느 시점에 인라인 RayQuery 트래버설 또는 매 프레임 TLAS 빌드가 Blackwell(RTX 5080)에서 비정상적으로 길어져 TDR 이 나고 디바이스가 제거된다. 트래버설을 길게 만드는 것이 우리 입력(비유한 변환·NaN 광선·UPLOAD 힙 BLAS)인지 드라이버 결함인지는 아직 가르지 못했다. 무엇이 20~30초를 만드는지도 모른다.

06왜 개발 PC(RTX 4070 Laptop)에서는 재현되지 않는가

두 단계를 갈라 봐야 한다.

  • 단계 B(멈춤) — GPU 세대와 드라이버 경로가 다르다(Ada vs Blackwell). RT 유닛·BVH 트래버설·빌드 구현이 세대마다 다르므로, 같은 입력이 한쪽에서만 병리적일 수 있다. 개발 PC 에서 RT ON 으로 장시간 돌려도 멈춘 기록이 없다.
  • 단계 C(누수) — 개발 PC 드라이버는 죽은 디바이스에 대한 제출을 즉시 실패시켜 루프가 폭주하되 메모리를 잡지 않았다. 교수님 PC 드라이버는 대기 뒤 새 푸시버퍼를 잡았다. 그래서 «폭주 vs 기어감», «0MB vs 63GB» 로 갈렸다.

즉 «개발 PC 에서 재현 안 됨» 은 단계 B 와 C 양쪽의 드라이버 차이가 겹친 결과이고, 우리 코드의 문제가 없다는 뜻이 아니다. 단계 C 는 우리 코드가 만든 것이다.

07조치 — 재현 환경 없이 할 수 있는 것

교수님 PC 를 다시 쓸 수 없다는 전제로 짠다. 실험을 요구하지 않고, 다음 실행이 언제 어디서 일어나든 필요한 기록이 자동으로 남게 하고, 단계 C 를 코드로 끊는다.

①

디바이스 제거 감지 시 제출 중단 + DRED 자취·제거 사유·커밋 메모리 샘플을 파일로 기록반나절 · 0c9e139 cherry-pick + 충돌 해결

단계 C 가 사라져 64GB 누수와 검은 화면이 없어진다(멈춤 자체는 남음). 다음 발생 때 어느 커맨드에서 멈췄는지가 남아 5.2 의 1순위를 확정하거나 기각한다. test 이력의 0c9e139(GRenderer.cpp/.h·main.cpp 250줄)를 복원한다.

비유한 인스턴스 변환은 TLAS 에서 제외하고 주차 노드는 TLAS 에 넣지 않는다. 셰이더에서 N·V·광선 방향이 비유한이면 광선을 생략한다. 1-b·1-c 를 코드로 제거한다.

1-d 의 자극을 줄인다. 설계 v1 의 정석 항목과 일치한다.

⑤

시연용 스위치 — 커맨드라인 --no-rt 로 RT 기본 OFF30분

원인 확정 전까지 교수님 앞에서 멈추지 않게 하는 안전판. 단계 B 가 RT 경로라면 증상이 사라진다.

판정 기준 — 다음 실행 로그가 답한다

  • DRED 마지막 커맨드가 BuildRaytracingAccelerationStructure 또는 RayQuery 드로우 → RT 경로 확정. ②~④ 뒤에도 같은 자리면 드라이버 결함(1-d) 으로 판정하고 NVIDIA 포럼에 신고한다.
  • DRED 마지막 커맨드가 래스터 드로우·Present → 5.2 의 3순위를 다시 본다.
  • ⑤ 로 RT OFF 상태에서 멈춤이 없으면 RT 경로가 조건임이 확정된다(원인까지는 아님).

이 조치들은 모두 개발 PC 에서 빌드·디버그 계층 오류 0·화면 동일까지 검증할 수 있다. 구조 수정(프레임 비행, 할당자 분리)은 원인과 무관하게 설계 v1·「렌더러 수정방향」의 순서대로 진행한다.
